## CI 门禁

**结构**：GitHub Actions，runner 是实验室服务器上的自托管 runner（GPU 在那里）。每次推到 main、每个 PR 都会触发；同一时间只跑一个（两个 GPU 是共享的）。不用任何第三方 action：服务器用 git 协议连 GitHub 不稳定，被测的代码通过 REST API 按提交下载 tarball。脚本 `scripts/ci.sh`。

| 阶段 | 内容 | 时间 | 拦截条件 |
|---|---|---|---|
| A | 单元测试（Python 6 个、edit 参数修正和输出截断 13 个）；预取节点在 20 道金丝雀题上的 hit@10 | 约 1.5 分钟 | 单测失败；预取命中低于 `data/ci-reference.json` 里的参考值（11） |
| B | 完整流程跑 20 道金丝雀题，官方判分 | 约 45 分钟 | 出现任何基础设施错误；通过题数低于下限（8） |

**怎么避免误拦**（方案第十节的问题）：确定性的节点指标（预取命中）没有噪声，所以要求“一点都不能变差”；端到端通过率有噪声（同一份代码跑两次差 5 个点），所以只设一个下限：金丝雀此前 6 轮（基线 3 轮、闭环案例 1 之后 3 轮）在 11 到 15 道之间，下限 8 道低于其中最差的一轮 3 道，噪声拦不住正常改动，只有明显变坏才会拦下。

**三次运行**

| 运行 | 提交 | 结果 | 说明 |
|---|---|---|---|
| 43861362405 | b5d60be（预取 v2 + CI 本身） | 失败 | 阶段 A 通过；阶段 B 20 道全部基础设施错误。原因：工作区里的 `node_modules` 是指向主仓库的软链接，而 `harness/pi` 会被挂进每个任务容器，软链接在容器里指向不存在的路径（`ERR_MODULE_NOT_FOUND`）。改为硬链接复制（`cp -al`，瞬间完成、不占空间） |
| 43862235599 | c84ef2e（修正上面的问题） | 通过 | 单测全过；预取命中 11（参考 11）；金丝雀 13/20 通过（下限 8），基础设施错误 0 |
| 43864029938 | PR #1（故意的退化） | **被拦下** | 见下 |

**被拦下的退化（PR #1）**：改动看起来是一次正常的提速：预取节点会对 issue 里的每个符号跑一次 `git grep -l -w`，给提到它的文件加一点分；PR 把这一步删掉，理由是“定义已经带了主要信号”。开 PR 之前先离线跑过 `scripts/prefetch_eval.py canary`：金丝雀命中从 11 降到 10。CI 阶段 A 测出同样的结果并失败：`prefetch regression: 10 < 11`，阶段 B 没有启动。PR 已关闭、分支已删除。

找这个例子时顺便看到：去掉双下划线过滤、把定义权重改成不分特异性、只要求精确路径、过滤短符号，这几种改动在金丝雀上都还是 11；只取前 5 个符号、去掉模块名信号反而是 12。金丝雀只有 20 道，预取指标对很多改动不敏感。预取是确定性的、整个开发集 100 道也只要几分钟，后续可以把阶段 A 的预取检查扩到整个开发集。

**局限**：私有仓库在 GitHub 免费账户下不能设置“必须通过检查才能合并”的分支保护，所以现在 CI 失败是一个红色的检查结果，不是强制阻止合并。仓库公开后可以打开分支保护。

## 闭环案例 2：预取节点（hit@10 57% → 70%）

**看板发现**：基线失败归因里，预取是“最早偏离”最多的节点（106 次失败里 56 次）；开发集上的 hit@10 只有 57%。闭环案例 1 先做了复现节点（问题更具体），这次回到预取。

**定位**：预取是确定性的，所以可以离线逐题看排名（`scripts/prefetch_eval.py`，只有这个脚本读参考补丁）。43 道没命中的题分三类：参考文件根本没进候选 20 道、进了但排在 10 名之后 15 道、一个候选都没有 8 道。逐题看排名靠前的文件，主要原因：

| 原因 | 例子 |
|---|---|
| 定义按行计分：一个文件里每出现一次 `def 符号` 就加 3 分 | issue 里提到 `__init__`，定义了 20 个 `__init__` 的大文件拿到 60 分，挤掉真正相关的文件 |
| 被提到的路径匹配了太多文件 | issue 里写了 `__init__.py`，仓库里所有 `__init__.py` 各加 5 分 |
| 带前缀的路径匹配不上 | issue 里贴的是 `site-packages/django/db/models/query.py`，仓库里是 `django/db/models/query.py` |
| 符号是模块级变量 | `FOO = ...` 不算定义，找不到 |
| issue 里只有自然语言 | “postgresql 客户端”“runserver” 这类词指向目录和模块名，但旧版只看代码符号，8 道题一个候选都没有 |

**修改（v2，提交 b5d60be）**：按检索里的词权重思路给每个信号按特异性加权：同一个（文件、符号）只算一次，权重 3 × min(1, 3 / 定义它的文件数)；双下划线名字不参与；匹配超过 5 个文件的路径忽略；路径按后缀匹配；模块级赋值算定义；issue 里的词如果是目录或模块名，按逆文档频率加一点分，几个词落在同一路径上再多加一点。

**结果（确定性，离线全量）**

| | v1 | v2 |
|---|---|---|
| 开发集 hit@10 | 57/100 | 70/100 |
| 参考文件没进候选 | 20 | 14 |
| 排在 10 名之后 | 15 | 16 |
| 一个候选都没有 | 8 | 0 |
| 金丝雀 hit@10 | 8/20 | 11/20 |

逐题看：15 道从没命中变成命中，2 道从命中变成没命中（django-15280、pytest-6197）。

**回归检查**：v2 和 CI 一起上线，CI 第二次运行跑完整流程，金丝雀 13/20 通过，在此前 6 轮的范围内（基线 13、11、12，闭环案例 1 之后 15、13、11），没有变差。端到端也没有看得出的提升，这和基线里的观察一致：预取没命中的 129 次里，有 73 次实现节点自己找到了正确的文件并通过。预取命中率提高的价值主要在于少走弯路（实现节点的 token），这个要在最终报告里和基线对比。

**要提醒的地方**：v2 是看着开发集上没命中的题改的，开发集上的 70% 有过拟合的成分。报告集（留出题）上的预取命中率才是它的真实水平，见“最终报告”。

## 闭环案例 3：实现节点的 edit 工具

一句话：新工具把参数格式错误清零了，但其他指标没有变好，所以没有采用；顺带发现这个问题在现在的代码下已经不严重。

**看板发现**：基线 3 轮里 edit 调用 1,139 次，99 次没通过参数校验（8.7%）；只看实现节点，3 轮分别是 29/217、24/244、20/229（9% 到 13%）。按形状分：49 次是模型把 JSON 混进了 XML 格式的工具参数（Qwen3.6 的工具调用是 XML 风格，Pi 的 edit 要的是嵌套数组 `edits: [{oldText, newText}]`，模型经常把嵌套写乱），24 次把 `path` 写进了每一项 edit 里，17 次把 `edits` 写成了字符串（大多也是混写）。出错后的下一次改文件成功了 78/99 次，也就是说多数时候只是浪费一轮。

**修改**（提交 8e918be）：
1. 参数修正 v2：`path` 写在每一项里且都相同时提到顶层；`edits` 是字符串时从里面找回 `path`，再交给原有的“按文件内容核对”的修正。离线重放基线里的 99 次失败：能修好 24 次。
2. 平铺的 edit 工具：同名、同样的执行逻辑，参数改成 `edit(path, oldText, newText)`，一次只改一处，从根上去掉嵌套。开关 `I2P_EDIT_TOOL`。

**怎么测**：单节点重测。两组都从基线第 1 轮存下的实现节点输入出发，重跑实现节点和紧接着的校验（`i2p rerun-node --until validate`）；代码完全相同，只有 `I2P_EDIT_TOOL` 不同（`nested` 是 Pi 原来的 edit 加参数修正 v2，`flat` 是新工具）；两组同时跑、各并发 4，负载条件一样。脚本 `scripts/edit_tool_ab.py`，逐题配对。

| 指标（实现节点，100 道） | Pi 原来的 edit | 平铺 edit | 配对差（平铺 - 原来） | 95% 区间 |
|---|---|---|---|---|
| 参数没过校验的 edit 调用 | 6/175（3.4%） | 0/189 | 每题 -0.06 次 | [-0.11, -0.02] |
| 实现一次过 | 80% | 75% | -5 个点 | [-12, +2] |
| 交出结果 | 100% | 96%（3 次耗尽轮数、1 次超时） | | |
| 每题 token | 75.1 万 | 75.8 万 | +0.7 万 | [-6.8 万, +8.6 万] |
| 每题工具报错 | 2.97 | 2.87 | -0.10 | [-0.68, +0.45] |
| 每题模型请求 | 34.4 | 36.8 | | |

- 目标指标变好了：参数格式错误清零，区间不含 0。
- 但其他指标都没有变好。“实现一次过”低 5 个点，区间跨 0，按规则不解读；逐题看，原来过、平铺没过的 9 道里有 2 道平铺这边一次 edit 都没调用（用 bash 改的文件），说明这部分差异和 edit 工具无关，是噪声。平铺工具每处改动单独一次调用，平均每题多 2.4 次请求。
- **没解释清楚的地方**：原来那组在现在的代码下只有 3.4% 出错，明显低于基线的 9% 到 13%。参数修正 v2 只在这组里起作用了 3 次，不足以解释这个差距；其余代码改动都不碰 edit。基线里的失败高度集中（第 1 轮 29 次里有 15 次出在 2 道题上，模型一旦写乱就连续写乱），所以更可能是轮次之间的波动。这一条如实记下，不归功于任何修改。

**决定**：默认用 Pi 原来的 edit 加参数修正 v2，平铺工具保留为开关（提交 b105e66）。理由：剩下的格式错误很少，而且 6 次出错后下一次改文件全部成功；平铺工具没有带来任何结果上的改善，还多了请求数；自定义的部分越少，跟进 Pi 版本升级越省事。参数修正 v2 保留：它只在能核对的情况下改参数，没有副作用。

和闭环案例 1 是同一个教训：把看得见的症状消掉，不等于结果变好，要看真值指标才能判断。数据：`runs/cl3-nested-r1`、`runs/cl3-flat-r1`，汇总 `var/logs/cl3-ab.json`。

## 最终报告

**怎么跑的**：报告集是从 288 道留出题里按仓库 × 难度分层抽的 100 道（种子 0），在任何运行之前写死在 `data/report-set.json`；开发过程中没有看过这些题。代码版本 b105e66（含闭环案例 1、2 的修改，edit 用 Pi 原来的工具）。每题跑 3 次，只跑这一次，不根据结果再改代码重跑。脚本 `scripts/run_report.sh`，数据 `runs/final-r1..r3`，汇总 `runs/funnel-final-r1+final-r2+final-r3.md`；三轮都已导入 Langfuse。

| 指标 | 结果 | 95% 区间（按题自助法） |
|---|---|---|
| **隐藏测试通过率** | **68.3%** | [60.3%, 76.0%] |
| 稳定性（3 次都通过的题） | 57.0% | |
| 预取命中（参考补丁改的文件都在前 10） | 70.0% | [61.0%, 79.0%] |
| 复现测试有效 | 48.7% | [41.3%, 55.7%] |
| 实现一次过 | 75.3% | [69.7%, 80.7%] |
| 修复挽回（52 道题有样本） | 34.9% | [22.8%, 47.4%] |
| 评审结论与隐藏测试一致 | 73.3% | [65.8%, 80.5%] |

三轮分别通过 68、67、70 道。300 次运行里 2 次整题超时（1 小时上限），没有基础设施错误。

**失败归因**（95 次没通过，每次算到第一个真值没过的节点）：预取 45、复现 31、评审 11、实现 8。和基线时一样，预取排第一主要因为它排在最前面；预取没命中的 90 次里，有 45 次实现节点自己找到了文件并通过。

**评审**：288 次给出结论，276 次 approve，其中 75 次放过了没修好的补丁；12 次 request_changes 里 10 次拦对了、2 次误杀。评审依然几乎不提供信号，是下一步最值得改的节点。

**成本**：每题平均 137 万到 140 万 token（中位数约 110 万，绝大部分是命中前缀缓存的输入），平均 11 分钟（中位数约 8.5 分钟）；每轮 100 道、并发 8 约 2.5 小时。

**怎么读这些数字**：
- 预取在留出题上是 70.0%，和开发集上 v2 的 70% 一样。闭环案例 2 担心的过拟合没有出现。
- 开发集基线是 64.7%（代码 7affc18），但题目不同、代码也不同，两个数不能相减当作提升。这份报告是系统当前在没见过的题上的水平。
- 题量是 100 道，区间宽约 16 个点，只能看大致水平。

# 阶段 2 报告：服务化

日期：2026-11-16 · 设计见[决策 0005](../decisions/0005-service.md)

## 完成标准

| 标准 | 结果 |
|---|---|
| 给测试仓库的 issue 打标签，自动开出 PR | 达到：私有沙盒仓库的 3 个 issue 打上 `i2p` 标签后，服务自动开出 PR #4、#5、#6，三个补丁都改对了地方 |
| 同时提交多个任务能排队执行 | 达到：3 个任务、2 个 worker，各拿 1 个，第 3 个排队，前面的做完后自动接上 |
| 杀掉一个 worker，任务被接手且没有重复开 PR | 达到：一个注入了故障的 worker 开完 PR 后立即崩溃、没来得及记账；消息重投给新 worker，它找到已有的 PR 并记下；每个任务都只有一个 PR |

## 端到端演示

沙盒仓库：`zz1403489227-crypto/issue2patch-sandbox`（私有）。代码是 pytest 在某道开发集题目基线时的版本（`i2p-base` 分支，和那道题的 Docker 镜像内容一致），`main` 上多了一个提交，埋了两个 bug。

| issue | 内容 | PR | 改动 |
|---|---|---|---|
| #1 | 那道 SWE-bench 题的原文：参数里的 `.[` 在报告标题里被换成 `[` | #6 | 去掉 `getmodpath` 里多余的 `.replace(".[", "[")` |
| #2 | 埋的 bug：`approx` 默认相对误差是 1e-4，文档写的是 1e-6 | #4 | 改回 1e-6 |
| #3 | 埋的 bug：`importorskip(minversion=...)` 在版本正好等于最低版本时也跳过 | #5 | `<=` 改回 `<` |

三个任务的校验都通过，独立评审都是 approve。PR 描述里写明“需要人工评审后再合并”，并附上校验和评审结论。

链路：GitHub `issues.labeled` 事件 → smee.io → 服务器上的转发程序 → `POST /webhooks/github`（HMAC 签名校验）→ Postgres 建一行 `queued` → RabbitMQ 只发任务号 → worker（预取 1，手动确认）→ 用 REST API 取仓库当前 `main` 和镜像版本之间的差异，在沙箱里补上，并按目录树哈希核对和 `main` 完全一致 → 八个节点 → 用 Git Data API 在任务的基线提交上建一个提交、指向 `i2p/<任务号>` 分支 → 开 PR → 记账、确认消息。

## 过程中遇到的真实问题

| 问题 | 怎么查到的 | 怎么定的 |
|---|---|---|
| webhook 处理器读了一个已经不存在的字段，前 3 次事件返回 500 | API 日志里的 KeyError | 基线提交改由 worker 开工时解析；重新打标签触发 |
| 从服务器 `git fetch` GitHub 时好时坏 | 手工复现：IPv6 线路直接不通；走 IPv4 时，往空仓库拉 2 秒成功，往已有对象的仓库增量拉 90 秒后 TLS 连接被掐断（GnuTLS -110），而且并发时更容易失败；同一时间 api.github.com 连测 3 次都在 1.3 秒左右返回 | 不再用 git 协议：同步代码用 compare 接口直接取差异，发布分支用 Git Data API（建 blob、树、提交、分支引用），所有请求强制 IPv4、失败重试。这也是 GitHub App 类集成的常见做法 |
| 用 `gh` 重新投递 webhook 需要 `admin:repo_hook` 权限 | gh 报错 | 不扩大权限，改为移除再加上标签重新触发 |
| RabbitMQ 4.1 的优先级不是严格的 | 实测 + 官方文档 | 升级到 4.3（见决策 0005） |

## 权限和安全

- 开 PR 的 token 由用户生成，只对沙盒仓库生效：代码读写、PR 读写、issue 只读。用它访问主仓库 `issue2patch` 返回 404，确认权限范围是对的。
- token 存放在服务器上一个权限为 600 的文件里，日志和报错里出现时会被抹掉。
- webhook 只订阅 issue 事件，用服务器上的密钥做 HMAC-SHA256 签名，服务端校验失败返回 401。
- 服务的所有端口只绑定 127.0.0.1；对外唯一的进口是 smee.io 转发程序主动发起的出站连接。

## 局限（如实写进 README）

- 只在单机上验证过多 worker，没有做过真实的多用户负载。
- 沙盒仓库是演示用的：埋 bug 的那个提交在仓库历史里看得到，Agent 理论上能通过 `git log` 看到改动；这不影响要验证的服务机制，但不能当作解题能力的证据。
- 一个仓库对应一个预先构建好的运行环境镜像（`data/repos.json`）；接入新仓库要先给它准备镜像。

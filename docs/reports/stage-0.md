## 附录 B 的三件事

1. **Pi 接本地 Qwen3.6 的工具调用稳不稳：协议层稳，`edit` 工具不稳。** 532 次模型请求全部以工具调用结束，没有一次 HTTP 错误，也没有服务端解析不出的工具调用。按工具看：bash 397 次（38 次报错，基本是命令本身失败，比如测试不过，属于正常反馈）、read 98 次（2 次报错）、write 11 次（0 次）、submit 9 次（0 次），而 **edit 17 次里 6 次报错，其中 5 次是参数没过 Pi 的校验**：Pi 的 edit 要求 `path` 加一个由 `{oldText, newText}` 对象组成的 `edits` 数组，模型有 3 次把 `edits` 整个当成一个 JSON 字符串传，2 次干脆用了平铺的 `oldText/newText` 写法。pytest-6202 的实现节点就是因为 3 次 edit 都失败，最后一行源码都没改成，靠修复节点才补上。这是阶段 1 要处理的第一个工程问题（方案风险表第一条），会记进决策记录。
2. **SWE-rebench 能不能接：按方案的定义接不了。** 模型在 Hugging Face 上的发布时间是 2026-04-15。SWE-rebench 排行榜数据集最新的月份是 2026-03；SWE-rebench V2 的 Python 题最晚到 2025-07；另查了 SWE-bench-Live，最晚到 2025-09。也就是说，公开数据里没有“晚于模型发布”的 Python 题。另外，SWE-rebench 的镜像在 Docker Hub 上，服务器连不上 Docker Hub（配置的镜像加速站都失效了），实测拉取失败。
3. **Harbor 判分怎么接：只核实了一半。** 本项目环境里装了 Harbor 0.26.0，读了它官方的 SWE-bench 适配器。适配器生成的任务直接 `FROM` 同名的 SWE-bench 镜像，参考解是一段 `patch` 脚本。所以对接方式很直接：用适配器生成任务，把参考解换成流水线产出的补丁，然后用 Harbor 的 oracle 方式判分。实际生成任务那一步需要在服务器上运行从 GitHub 拉下来的 Harbor 适配器代码，被本机的权限策略拦下了，没有执行。阶段 0 的判分先用官方 SWE-bench 判分程序（Harbor 适配器自己也是拿它做对齐验证的）。

## 阶段 0 里发现、留给阶段 1 的问题

- **edit 工具参数格式错误**（见附录 B 第 1 条）：17 次里 5 次没过参数校验，直接导致一道题的实现节点没改成代码。
- **Agent 把轮数预算用光还没提交**是最大的问题：17 次 Agent 调用里 8 次。剩 5 轮时插入的“马上提交”提示（Pi 的 steer）在 8 次里都没起作用，模型照样继续调工具。这是阶段 1 闭环案例的头号候选。
- **复现节点越界**：django 那道题的复现 Agent 顺手去改了源码，按契约被整体回滚，又因为没提交，复现测试也没留下。
- **预取对纯描述型 issue 无效**：sympy 那道题的 issue 里没有文件名、模块名或可识别的符号，预取一个候选都没给出，后面三个 Agent 节点全部耗尽预算。
- **评审节点 5 次全部 approve**，包括两道隐藏测试没过的题；误杀率和漏放率要到阶段 1 有了足够样本才能算。

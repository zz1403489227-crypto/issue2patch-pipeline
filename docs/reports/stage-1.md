### 归因要谨慎读的地方

按方案的定义，失败算到“第一个没过检查的节点”。预取排在最前面，所以它被算得最多；但预取没命中并不致命：预取漏掉参考文件的 129 次里，有 73 次实现节点自己找到了正确文件并且通过了隐藏测试。所以这张归因表回答的是“最早从哪一步开始偏了”，不是“哪一步导致了失败”。挑闭环案例时我没有直接拿最大的那一项，而是看哪个节点的问题最具体、能确定性地改。

## 闭环案例 1：复现节点的测试有效率

一句话：第一次修改治好了症状（提交率），但真值指标没动；顺着真值往下查，发现病根在我们自己的节点契约，第二次修改让复现有效率提高了 9.3 个点。

### 看板发现

复现节点的有效率只有 42%（测试在原代码上失败、打上参考补丁后通过），“没交出测试”是最大的一类：300 次里 99 次。

### 第一次：定位到“写好了却没提交”

- 96 次复现节点耗尽 40 轮预算；其中 87 次 Agent 其实已经写好了测试文件（中位数在第 22 次工具调用时写出），只是一直在跑、在改，没调 submit。没提交就按契约整体回滚，测试被丢掉。剩 5 轮时插入的“马上提交”提示发了 408 次，几乎无效。另外，最后一轮里发出的 submit 也会被丢弃（预算检查先于工具执行）。
- 修改：最后 3 轮用 Pi 的 `setActiveToolsByName(['submit'])` 只留 submit 工具并说明原因；最后一轮里的 submit 照常执行。改动在 harness 层，四个 Agent 节点都受影响；开关 `I2P_FINALIZE`。
- 结果（单节点重测 2 轮，逐题和基线配对）：复现节点交出测试的比例 69% → 95%，耗尽率 30% → 4%；**但有效率 42.5% → 41.5%（差 -1.0 个点，区间 [-9.0, +6.5]），没有变化**。多交上来的测试几乎都是无效的：“原代码上失败、打上参考补丁后也失败”从 18 次涨到 39 次（第 1 轮）。

### 第二次：定位到“测试根本没跑起来”

- 把无效测试在原代码上的运行日志分类：第 1 轮重跑里 43 个“打上参考补丁后也失败”的测试，有 18 个根本没跑起来（模块导入失败、收集失败），其中 12 个是 Django 报 `Failed to import test module`。
- 看日志：这些 Django 测试都写着 `from .models import ...`，而 Agent 当时确实在 `tests/i2p_repro/` 下建了 `models.py`，测试在它自己的会话里是能跑、能失败的。是复现节点的确定性契约把 `models.py` 当成越界改动删掉了：契约只保留测试文件和 `__init__.py`。问题出在我们自己的代码上，不在模型。
- 修改：(1) 契约改为保留 Agent 新建的测试目录里新增的所有文件（以及文件名带 `i2p_repro` 的新文件），改动已有文件仍然回滚；(2) 加一道兜底：测试在原代码上“没跑起来”（导入失败、收集失败、没跑到任何测试；检测只用原代码上的输出，不看参考答案）时，把报错退回给 Agent 修一次，限 15 轮。检测器上线前在已有 4 轮数据上离线核对过：标记出的都是无效测试，没有一个有效测试被误判。
- 结果（单节点重测 3 轮，逐题和基线 3 轮配对）：

| 指标 | 基线 | 第二次修改后 | 配对差 | 95% 区间 | 结论 |
|---|---|---|---|---|---|
| 复现测试有效率 | 42.0% | 51.3% | **+9.3** | [+3.0, +15.7] | 变好（超过 5 个点，区间不含 0） |
| 复现节点交出测试 | 67% | 96% | | | |
| 复现节点每次 token | 48.4 万 | 44.8 万 | | | |

- 贡献主要来自契约修正：300 次里 41 次保留了辅助文件；“退回修一次”只触发了 7 次、修好 1 次。
- 剩下的无效测试：300 次里 84 次“打上参考补丁后也失败”、49 次“在原代码上就通过”。这两类不靠参考答案很难识别，留作阶段 3 的候选（方案扩展点“复现节点并行：多写几个候选测试，只留确实失败的”）。

### 回归检查：20 道金丝雀，完整流程各 3 轮

| 指标 | 基线 | 修改后 | 配对差 | 95% 区间 | 结论 |
|---|---|---|---|---|---|
| 隐藏测试通过率 | 60.0% | 65.0% | +5.0 | [-1.7, +13.3] | 无法区分（没有变差） |
| 复现测试有效率 | 35.0% | 58.3% | +23.3 | [+6.7, +41.7] | 变好 |
| 实现一次过 | 80.0% | 68.3% | -11.7 | [-23.3, -1.7] | 变差，原因见下 |
| 修复挽回 | 33.3% | 50.0% | +16.7 | [-20.0, +60.0] | 样本太少 |
| 评审一致 | 61.4% | 65.8% | +4.4 | [-5.3, +14.9] | 5 个点以内，不解读 |

“实现一次过”下降不是实现节点变差了，而是校验变严了：可用的复现测试从 60 次里 28 次增加到 48 次，校验多了一项“复现测试要通过”。第一次校验因为复现测试没过而失败的次数从 4 次升到 9 次；“第一次校验失败、但补丁其实通过了隐藏测试”的误报从 4 次升到 9 次。也就是说，更多的复现测试一方面让校验更有用，一方面也把剩下那些无效测试的误报带进了校验。端到端通过率没有变差。这条误报会作为下一个闭环案例的候选：校验节点怎么对待“可能是错的复现测试”。

### 结论

- 保留第二次修改（契约修正和退回修一次），也保留第一次修改（最后 3 轮只留 submit）：后者单独看没有提高有效率，但让 95% 以上的复现节点交出结果，是第二次修改能起作用的前提，而且没有观察到副作用。
